# 个人课程、科研与竞赛统一安排：V1 建模审查与实现规格

版本：planner.v1.1 / 2026-09-21

状态：正式开发基线。原始文件保存在 `reference/`。本版本修订了保护、记账、协议和实现顺序；所有产品行为仍须通过新版验收。

## 0. 结论、依据与范围

建议实现“人工决定任务价值与验收条件、约束模块安排时间、执行日志驱动滚动重排”的单人规划器，而不是学习收益最大化器。

本规格基于所附《个人学业与项目的自适应学习安排：学术、开源与产业界深度研究》全文。主要继承其“下一步做什么与什么时候做分层”“不统一加权异质价值”“7–14 天滚动安排”“科研 time-box + checkpoint”“排不下要返回未安排与原因”的框架。下面的数据结构、状态机、默认数字、目标顺序和接口是本轮工程设计，不是报告已验证过的完整系统。

原始规格报告曾核对 OR-Tools 文档，并报告 41 项语义断言通过。本次仅收到规格与验收文档，未收到或运行其引用的校验代码、结果文件和 JSON 示例。原有通过状态不适用于本版本；本版本是实现合同，不是已完成软件的说明。

### 必须区分的四种事实

| 名称 | 含义 | 不能推出 |
|---|---|---|
| 实际投入 | 已确认执行记录里的专注时间 | 完成相同比例的交付物 |
| 剩余工作量 | 当前对还需投入时间的人工估计 | 客观确定的工期 |
| 已完整预留 | 当前模型下为剩余需求排足时间 | 现实已经完成、必然按时完成 |
| 实际完成 | 满足该任务类型的验收或检查点关闭规则 | 学会、实验成功、掌握度达到某概率 |

### 全局默认值

| 参数 | 推荐默认 | 理由 | 可替代方案 |
|---|---|---|---|
| 资源范围 | 一名用户的一条注意力资源 | 防止课程、科研和竞赛重复占用同一时间 | 后续增加机器等独立资源 |
| 展开窗口 | 未来 14 天 | 兼顾周计划与有限估计可信度 | 7 天；窗口更远仅展示需求，不承诺可行 |
| 日程网格 | 15 分钟 | 足以排常见学习块，易读易检验 | 5 分钟；需要同步调整所有约束 |
| 时间记录 | 执行日志精确到秒；工作块到分钟 | 不把显示网格误当实际耗时 | 手动填分钟也可，但注明来源 |
| 近期冻结 | 已发布计划中开始于未来 24 小时内的整个工作块；常规重排保留，调整提案须集中确认 | 避免频繁改变近期承诺 | 12/48 小时或严格模式；人工锁仍需明确逐项授权 |
| 可拆任务最小块 | 30 分钟，末尾允许一个更短的完整收尾块 | 避免碎片，同时避免剩 15 分钟永远排不下 | 15/45 分钟或任务覆盖 |
| 偏好块长 | 60 分钟；不设普适的硬性最长学习时长 | 不把偏好伪装成个体疲劳规律 | 用户设置连续时长上限与固定休息 |
| 未分配缓冲 | 每天可用容量的 20%，按网格向下取整 | 显式留出未预见工作空间 | 默认启用且界面明确展示；已自行留有裕量可设 0 |
| 任务重要性 | 新任务默认 PREFERRED；COMMITTED 必须由人选 | 不把领域或截止日期当作自动价值判断 | 项目模板可给建议，但任务存独立取值 |
| 求解预算 | 整个请求 2,000 ms | 是交互超时配置，不是性能承诺 | 500 ms / 5 s，由本地测试调整 |
| 常规重排 | 执行反馈后有重大变化；每日一次整理；主动请求 | 避免每次鼠标修改都洗牌 | 全手动模式 |
| 自动续探索预算 | 关闭 | 防止探索无限续杯 | 明确授权后的独立新轮次 |

所有数值均为可修改的产品默认值，不是个人成功率或经验证的最佳学习参数。

## 1. 对象与状态

### 1.1 Project

必要字段：`id, revision, name, category(COURSE|RESEARCH|COMPETITION), status(ACTIVE|PAUSED|CLOSED), default_importance, created_at, closed_at, closure_reason`。

项目是组织容器，不是一份额外工作量。共同技能用文字标签即可；V1 不从标签生成先修关系或学习收益。

状态：`ACTIVE ↔ PAUSED → CLOSED`。关闭项目不能暗中将任务标记完成：必须先处理未关闭任务，明确选择完成验收、取消、迁移。项目暂停后停止新增自动安排；受保护预约若仍存在，先显示将释放的块并取得明确操作授权。项目模板修改不追溯重写现有任务优先级。

默认只允许一个任务属于一个项目，避免多项目重复计工时。替代方案是多标签展示，但必须保留唯一任务 ID 和唯一工作量。

### 1.2 Task

| 字段组 | 必要字段与语义 |
|---|---|
| 身份 | `id, revision, project_id, title, kind`，kind 为 DELIVERABLE 或 TIMEBOX |
| 生命周期 | `lifecycle: DRAFT|OPEN|IN_PROGRESS|REVIEW|PAUSED|DONE|CANCELLED` |
| 人工判断 | `importance: COMMITTED|PREFERRED|OPTIONAL`, `manual_order` |
| 时间 | `release_at`, `due_at?`（目标日期，可迟到）, `cutoff_at?`（禁止新安排晚于此时） |
| 剩余需求 | `remaining_work_seconds`, `remaining_source`, `remaining_as_of`, `estimate_revision` |
| 可拆性 | `splittable`, `minimum_block_minutes`, `allow_rescue_partial=false` |
| 依赖 | `dependencies: [{task_id, relation: FINISH_TO_START}]` |
| 完成规则 | 交付物的验收标准和证据；探索的预算、累计投入、检查点和决策 |
| 输入要求 | `action_required[]`，例如重新估计、补日志、检查点未填写 |
| 审计 | 创建时间、完成事件时间、确认时间、取消原因、范围变更历史 |

`blocked`、`overdue`、`FULL/PARTIAL/NONE` 是派生属性，不混入生命周期枚举。任务可以同时是 IN_PROGRESS、依赖暂不可执行、已过目标日期、只排了一部分。

主要转移：

- DRAFT：缺验收条件或可信的工作值，不能自动安排；信息补齐后变 OPEN。
- OPEN：安排进日历仍为 OPEN；第一次实际投入后才变 IN_PROGRESS。
- IN_PROGRESS：交付物送验，或探索预算用尽，进入 REVIEW。
- REVIEW：验收或检查点关闭成功变 DONE；需要返工变 IN_PROGRESS，并重新估计。
- OPEN/IN_PROGRESS/REVIEW 可暂停或取消；恢复时重新检查依赖、期限和估计。
- DONE 不自动重开。显式重开创建新 revision，重新检查后继尚未执行的块；既有实际记录不回滚。

交付物“估计已经耗尽但成果未就绪”仍是 IN_PROGRESS，附 REESTIMATE_REQUIRED，不冒充 REVIEW 或 DONE。

### 1.3 CalendarWindow / FixedEvent / WorkBlock

可用窗口说明允许工作的时间；固定事件说明不能被自动排程占用的时间。二者均不等于任务执行记录。

`WorkBlock` 字段：`id, task_id, plan_id, start, end, reserved_minutes, planned_work_seconds, rounding_padding_seconds, protection(NONE|FROZEN|MANUAL), state, conditional_on[], coverage_state, validity, start_eligibility`。

状态：`PLANNED → RUNNING → RECORDED`；未执行且确认跳过变 SKIPPED；未来计划被替换变 SUPERSEDED；用户关闭任务释放未来时段变 CANCELLED。时间自然经过但没有日志时标 EXECUTION_UNCONFIRMED，不自动推断做了或没做。

工作块稳定 ID 必須跨重排保留。相邻同任务块可以在界面合并显示，但不能借此改变受保护块的身份或边界。

默认 V1 的自动块和人工锁定工作块都满足网格。非网格锁块返回 OFF_GRID_LOCK，不静默取整；外部课程、会议保持原时间，空闲窗口在扣除它们后向内对齐网格。替代方案是改用更细网格或支持任意分钟锁块，但需修改工时与舍入模型，不能只改前端。

### 1.4 ExecutionRecord 与 PlanSnapshot

执行记录字段：`id/idempotency_key, task_id, block_id?, started_at, ended_at, active_seconds, source(TIMER|MANUAL), interruption_note, outcome_note, artifact_refs, remaining_feedback, remaining_after_seconds?, recorded_at, supersedes_record_id?`。

专注时间不包括休息、离开、无人值守的计算等待。一次失败尝试仍是实际投入，不能为了提高效率指标而删除。同一时段不能被两条已确认专注日志重复计时；冲突日志可保存为待核实，但不能直接双重累计。重复提交相同 ID 与相同内容返回原结果；同 ID 不同内容报冲突。更正通过新版本记录，不覆盖原事实。

`PlanSnapshot` 至少保存：`plan_id, input_revision, generated_at, horizon, policy_version, solver_summary, blocks, assessments, unallocated, changes`。规划模块只返回建议，不修改实际完成状态。

默认用快照＋版本化事件，而不要求完整事件溯源框架。替代是更简单的关系表，但仍必须保留版本、幂等和修改审计。

## 2. 两类任务的完成规则

### 2.1 DELIVERABLE：明确交付物

例如：“提交概率论指定题目，保存题解文件并检查提交回执”。完成需要：验收条件满足、证据或文字说明保存、本人确认。完成确认时间与真正提交/验收事件时间可分别记录，以免晚录日志被误判成晚提交。

90 分钟的预计工时全部用完，不等于任务完成。只做完其中部分题目也不按时间比例自动折算成果完成度。实际已完成且确认验收时，剩余归零，关闭任务，并以此次明确关闭操作释放未来预约。操作界面应说明会释放哪些受保护块。

默认人工验收。替代方案是后续接入测试、提交回执等自动证据，但自动检查只能检查约定条件，不推断学会了。

### 2.2 TIMEBOX：限时探索

例如：“用 90 分钟调查方法 X，记录证据并决定继续、停止或改方向”。预算是最多获准投入的专注时间，不是研究必定解决问题所需的工期。

默认关闭条件：累计投入达到预算，并填写检查点及决策；也允许提前关闭，但需显式说明已获得足够判断依据并确认。检查点至少包含：尝试了什么、留下什么证据、当前知道或仍不知道什么、CONTINUE/STOP/PIVOT 决策。

预算耗尽但没有检查点：REVIEW，不再自动追加工作时段。否定性结果、仍不确定、决定停止都可以是合格检查点。“继续”只产生新任务或新预算提案，未经批准不安排新一轮。实质性的下一轮研究使用新任务 ID，保留前一轮时间与结论。

默认最后 10 分钟提醒整理记录，这 10 分钟在 90 分钟内部，不是附加工时。若整理成果本身需要较多工作，应新建交付任务。超预算的实际投入仍如实记录并提示超额，不篡改日志，也不反向伪造授权。

科研结果决定的分支不能提前激活。比如“只有方法 X 值得继续时才实现 X”，实现任务保持 DRAFT，直到检查点后人工激活。纯粹的“整理已有调查记录”可作为确定性后继处理。

## 3. 排程模型

### 3.1 时间口径与变量

V1 排一名用户的注意力；课程和固定会议占不可用时间，不与自学工作量重复扣减。机器等待不占注意力资源：实验拆成“启动”“等待外部结果”“检查结果”，V1 的等待解除由人确认，不估计机器排队分布。

固定事件存带偏移的时间，按配置时区展示；日容量按当地自然日计算。采用半开区间 `[start,end)`，相邻边界允许接触。所有时区必须明确，纯日期截止需用户确认具体时刻。循环日历展开到当前窗口，并处理重复/不存在的本地时刻；不能静默猜夏令时偏移。

设任务 i 的原始剩余工作为 W_i 秒，网格 q=15 分钟，日历预留需求：

`R_i = q * ceil(W_i / (60*q))` 分钟。

每个候选块 k 使用存在变量 x_ik、开始 s_ik、时长 d_ik、结束 e_ik。存在时 `e=s+d`；不存在时 d=0，所有相关顺序约束按存在性启用。`A_i = sum(d_ik)`，仅对 coverage_state=COUNTED 的未来工作块求和；`f_i=1` 当且仅当正需求任务 `A_i=R_i`。未验收的零工作量任务不能因此变成完成，也不能用 f_i 解锁后继。

完整预留时总舍入留白为 `60*R_i-W_i` 秒，放在最后一个块；部分预留不计这部分留白。日历占用、每日容量用完整块长度；探索预算与执行时间只用实际工作秒数。

例如剩 53 分钟，安排 60 分钟，其中 7 分钟是留白，不允许多消耗 7 分钟探索预算，也不把任务估计永久改为 60 分钟。

### 3.2 硬约束

| 规则 | 默认实现 | 边界/替代 |
|---|---|---|
| 单人不重叠 | 所有工作块与固定占用无重叠 | 多资源后端以后再加 |
| 可用时间 | 工作块完整位于扣除忙碌后的可用窗口 | 不自动使用睡眠或夜间时段 |
| release | 开始不早于释放时刻 | 不能因优先级高而绕过 |
| cutoff | 工作块结束不晚于禁晚时刻 | 除非用户明确改变任务规则 |
| 每日容量 | 当日未来预约不超过扣除已确认实际投入后的剩余上限 | 实际过去超额作为事实保存；未来上限截为 0 |
| 保护 | 人工锁定、近期保护块在常规重排中完整保留 | 允许生成尚未应用的调整提案；见第 11 节 |
| 工作量 | 总预留不超过舍入后的剩余需求 | 扩大任务范围须新估计与审计 |
| 可拆性 | 不可拆任务只有 0 个块或一个完整剩余块 | 现实中断后必须由人确认残量/重来 |
| 最小块 | 普通块至少 30 分钟 | 只有排齐全部剩余量时，最后一块可短于 30 分钟 |
| 依赖 | 有向无环、默认 finish-to-start、零滞后 | 不实现自动技能图、OR 依赖或未知研究分支 |

每日容量一律用秒计算，网格仅用于新增块。全天可用窗口扣除固定课程/会议后的时长为 F；缓冲 B=900*floor(buffer_ratio*F/900)，C=min(显式日上限或 F,F-B)。定义 H 为已确认的实际专注秒数，L 为计时器已发生但未结算的 active 段秒数，T 为 RUNNING 块从 now 到已确认结束时刻的剩余预约秒数，P 为其他未来日历保留秒数。必须满足 H+L+T+P≤C；各段跨日拆分，互不重复。未结算 active 段结算后由 L 转入 H，同一 session/segment 只能计一次。运行块已发生的休息不算 L，未来 T 暂按完整预约保守计容量。

可新增容量=max(0,C-H-L-T-P)。固定课程/会议只在 F 中扣减，不再进入 H；历史实际投入即使发生在原可用窗口外仍计入 H。舍入留白和待核实未来占位属于 P。已超上限的历史事实不回滚，停止新增预约，存量未来块按冲突流程处理。正在运行的块超过预计结束仍未停止时，要求确认新的结束时间；确认前暂停当日新增自动块，其他日期仍可规划。

若受保护未来块已超过剩余容量，返回保护冲突。不能将容量上限临时抬高而不告诉用户。缓冲是容量政策，不另加一个与“安排更多工作”互相矛盾的“最大化剩余空闲”目标。

### 3.3 部分安排和任务拆分

可拆任务默认允许部分安排：`0 < A_i < R_i`。含义只是“在当前窗口里预留了一部分时间”，未安排量必须返回；不能显示成成果完成百分比。跨越规划窗口的任务可以只安排本窗口的一部分，但不能声称窗口外也排得下。

不允许把多个碎片拼成要求连续的工作。180 分钟模拟赛不能用 6 个 30 分钟块替代。

对 cutoff 已进入当前规划窗口、又无法排齐的任务，默认不新增无望完整交付的部分投入；但已经存在的受保护块可以保留，明确显示承诺未满足。形式上：当 f_i=0 时，新自动块总长度为 0；已经受保护的预约不被删除。用户可显式设置 allow_rescue_partial，允许抢救性部分投入。

这条规则不禁止有长期价值的部分推进，也不自动判断部分成果有没有价值。它只是保守默认，尤其用于比赛报名关闭、作业提交关闭等不可继续提交的任务。

“拆执行时段”不会生成新任务；“拆成几个不同交付物”属于范围变更，必须由人确认新任务、工作量和依赖迁移。不能同时让原任务和新任务重复记剩余需求。V1 不做自动父子任务工期汇总。

### 3.4 依赖的两个层面

排程预测：A 尚未完成时，可以给 B 预留未来条件块，但前提是 A 的全部剩余工作也已安排，且 A 最后一个块结束不晚于 B 开始。多个 B 共享 A 时，A 只安排一次。

实际执行：B 开始时必须检查 A 已实际 DONE。A 仅排足时间、预算耗尽、进入 REVIEW、被取消，都不算完成。若 A 实际未通过验收，B 的条件预约被标记不可启动并触发重排，不向历史写入虚假的完成事实。

依赖环、缺失任务 ID 是输入错误。外部审批、机器结果尚未返回、研究分支尚未决定时，不编造完成日期；相关后继暂不激活。后继截止时间可以形成排程内部的祖先最迟完成界限，但不自动修改祖先任务的真实 due/cutoff 字段。

### 3.5 分层软目标：常规模式

不是把重要性、难度和科研价值混成分数，而是按以下层次比较计划：

1. **保护本窗口内有明确期限的 COMMITTED 目标的按时完整预留。**按第 11.6 节定义的目标时刻、人工顺序、稳定 ID 形成公开序列，依次优化每个目标的及时完整预留标志，而不是最大化完成任务数。目标不存在可行完整安排时，继续检查后续目标，不强行让所有任务都失败。
2. **减少远期已有日程改变。**先最少改变/删除旧工作块，再最小化时间位移。新增块与旧块删除区分；重建 ID 不能逃避变更计数。
3. **在剩余空间里推进人工候选队列。**按 COMMITTED、PREFERRED、OPTIONAL，组内按目标日期及人工顺序分配剩余投入。没有科学收益权重，也不按短任务数量奖励。
4. **改善摆放。**减少柔性目标的迟期、过多块和项目切换；其他指标一样时用稳定 ID 与较早可行时间确定性破平局。

稳定性置于一般新增任务之前是有意取舍：普通新任务不会天天打散已有计划。代价是远期旧任务可能占住空间。用户可用“重新平衡”模式将第 3 层移到第 2 层前，但人工锁定与近期冻结仍不解除；或把确实要保住的工作明确设成有目标日期的 COMMITTED 任务。长期不被安排的任务应在每周审查中提示，不自动无限升级重要性。

第一版先实现确定性贪心后端与独立校验器，再接入有时间预算的优化后端。上面的目标顺序是比较返回计划的公开规则，不要求第一版证明词典序最优。完整依赖链采用临时放置和回滚，避免后继失败时留下只为该目标增加的无用祖先块；已有或被其他任务共享的祖先块不回滚。

若后续使用分阶段优化，只有已证明的上层最优值才能标作最优；允许用当前可行值约束后续改进，但必须标注 HEURISTIC，不冒称严格最优。所有候选先经过校验，再以相同快照、模式和评分函数与重验旧计划、贪心结果比较，返回其中较优者。旧计划不合法时不参与比较。求解器状态与最终选中方案来源分别记录。

## 4. 超载、过期、连续空档与超时

| 情况 | 默认动作 | 解释与替代 |
|---|---|---|
| 总需求超容量 | 返回合法的部分计划＋未安排项 | 缩范围、延期、取消、改变人工顺序由人决定；不追加夜间时间 |
| 窗口内截止链不可完成 | 标识整条依赖链的不足，保留其余合法安排 | 不只检查各任务孤立的工时 |
| 连续空档不足 | 输出所需连续长度和当前最大合法窗口 | 只有任务确实可中断时才建议改可拆性 |
| soft due 已过 | 保留原日期，显示逾期，可排补救工作 | 不自动把截止改成明天 |
| hard cutoff 已过 | 不再新增工作，待用户关闭/批准新规则/新建补救任务 | 未完成不自动等于取消 |
| 期限在窗口外 | 可以安排部分，标 WINDOW_LIMIT，不宣称将来可行/必然迟到 | 扩大窗口只是一种用户选择 |
| 零估计但未验收 | REESTIMATE_REQUIRED 或 REVIEW | 不自动生成每天 15 分钟的无限续命任务 |
| 锁定与新会议/容量冲突 | PROTECTED_CONFLICT，不发布冲突计划 | 旧计划保留用于审计，但明确失效，用户决定解锁或改输入 |
| 未知历史执行 | 不扣预计工时、不自动重播旧块；要求补日志 | 相关已有未来预约可保留为待核实占位，不计作已证明可完成的需求覆盖 |
| 求解只有 FEASIBLE | 返回独立校验通过的当前解 | 标明尚未证明最优 |
| 求解 UNKNOWN/超时 | 先重验旧计划，再尝试确定性贪心兜底 | 未找到不等于证明无解 |
| MODEL_INVALID | 实现/建模错误，不归责为用户超载 | 返回错误与可重验的旧计划 |

兜底顺序：受保护块 → 按公开顺序处理目标及其未完成祖先 → 用最早合法空档放置合法块 → 不能放就返回剩余。无论何种后端，都经过同一独立约束校验器。旧计划只有按新快照仍合法才可保留为有效结果。

解释必须区分：PROVEN（当前离散模型内有直接容量/窗口证明）、POLICY（保护或人为规则造成）、NOT_PROVEN（本次算法没找到）。贪心没排进不能标成 NO_CONTIGUOUS_WINDOW，除非确实检查了所有合法空档。

可选任务允许不排后，普通超载不应使整个模型无解。若该模型返回 INFEASIBLE，应先检查固定/保护集合、依赖强制条件或实现错误。另一个“要求所有任务完整安排”的诊断模型无解，不等于“一个合法部分日程也不存在”。

## 5. 滚动重排与应用事务

默认重排触发：任务完成或取消、依赖解除/重开、日历/锁定改变、截止风险改变立即触发；普通预计变化累计达到 30 分钟触发；小改动在约 5 分钟内合并；每日一次整理或用户手动发起。阈值只减少扰动，不能延迟硬冲突检查。

每次顺序：读取带版本快照 → 对账日志与剩余量 → 排除历史/已关闭项 → 验证输入与保护集合 → 固定人工锁和近 24 小时旧块 → 求解远期可变部分 → 独立校验 → 生成变更清单 → 按版本原子应用。

近 24 小时只冻结旧块，不冻结所有空白时间；新任务可使用其中真正空闲的时间。块开始在冻结边界内则冻结整个块。不得为赶任务静默释放冻结区。自动保护调整可以组成一份待确认提案，不要求用户先逐块解冻再重新计算；人工锁定变化必须在提案中逐项明确勾选。

无效旧块不被伪装成合法保留。截止/可用性发生硬冲突时先报告；用户接受“释放这一块”后只解除该项保护，其他块保持。

正在执行的任务不能被优化器搬走。V1 在其结束并回填后才重估该任务。进行中但预计结束不明时，要求确认，不猜一个持续滚动的结束时间。其他独立任务可围绕已知固定占用计算；不能以不明残量证明它的后继可行。

应用方案必须使用 `base_state_revision`。求解期间发生新锁定、新执行记录或编辑，旧结果拒绝覆盖，返回 STALE_REVISION。缓存复用除版本与策略一致外，还必须满足第 11.7 节时间有效性条件；时间经过也可能使旧计划失效。无事件变化不应制造无意义变更。

## 6. 耗时估计与剩余工作量

### 冷启动

交付任务默认要求人工给出工作值，未知则 `remaining=null` 并停留 DRAFT；不凭课程名称填“准确的两小时”。可以先批准一个 30 分钟的任务梳理 timebox，再估算。科研调查可从 90 分钟预算开始，这是假设性的投入上限，不是完成工期预测。

可选记录 `[lower, working, upper]`，全部是主观范围，不叫 P50/P80。主计划默认用人工确认的 working 值；较保守方案使用 upper 另算压力情景，并显示哪个选择造成超载。不额外静默叠加 1.3 倍等隐藏工时系数。每日缓冲与任务估计分别展示。

### 更新规则

| 反馈 | 更新 | 备注 |
|---|---|---|
| 人报“还需 75 分钟” | 直接把剩余设成 75 | 不能再减去此次已执行时间 |
| 人确认“大致按计划推进” | `max(0,旧剩余-本次新增专注时间)`，标临时估计 | 只处理尚未记账的新日志；归零未验收必须复估 |
| 人报“受阻/返工，没有净推进” | 保留或上调剩余 | 已消耗时间仍如实计入实际 |
| 没有剩余反馈 | 保留旧估计并标陈旧，停止自动追加该任务的新块，提示补确认 | 不把时间经过当成进度 |
| 交付验收通过 | 剩余 0，DONE | 取消未来预约的授权包含在明确关闭操作中 |
| timebox 执行 | `max(0,预算-累计实际专注)` | 这是剩余授权，不是剩余科学问题 |

任务范围变化、严重中断、返工后重新估计。不可拆任务被中断不应默认“剩下一半即可”：需要人选择继续、重来或结束本轮。若本轮是限时探索，重来同样不能绕过剩余预算，需额外授权。

有历史后，先展示同类且规模可比任务的中位数/范围与样本数，不直接上深度模型。避免只收集完成任务而忽略超时、取消和开放任务；也不能把开放任务已经投入的时间当成完整工期。统计量替换估计器是后续能力，不改变日志和剩余量语义。

## 7. 模块输入输出协议

`plan(snapshot) -> proposal`。V1 推荐同步调用、JSON、版本化协议；异步队列可以后续替换。规划模块无权完成任务、批准预算或改变截止。

### 输入必须包含

`schema_version, request_id, state_revision, now, timezone, horizon, policy, projects, tasks, availability, fixed_events, day_capacity_minutes/容量规则, actual_focus_seconds_by_day, protected_blocks, previous_plan_id, previous_blocks/可读取的完整旧计划, explicit_protection_releases`。

完整旧计划必须作为快照内容或由受控存储按 ID 解析，不能只给一个无法解析的 ID。任务采用已经对账的剩余工作投影，不把全量原始日志交给求解器临时猜进度。

输入缺少截止时间的时区、存在循环依赖、同一 ID 多条互斥数据、负工时、非网格锁块等，返回结构化输入错误。任务估计缺失可以作为逐任务 INPUT_REQUIRED 返回，不必让不相关任务一起报错。

### 输出必须包含

- 基本：`plan_id, base_state_revision, validation, solver`。
- 计划：`blocks`，每块有稳定 ID、起止、工作量与留白、保护类型、启动条件。
- 逐任务：`task_assessments`，分别输出 coverage、input_state、horizon_state、dependency_state，定义见第 11 节；同时返回需求、计入覆盖的工作量、未覆盖量、forecast_end、截止判断及条件依赖。
- 未安排：`unallocated`，包括部分安排后的剩余，不只列 0 个块的任务；每项有原因码、证据等级、具体证据和需要人确认的取舍。
- 变更：`changes`，每个移动/删除/新增块的原因与旧新值。
- 告警：当前计划有效性、所有需求是否能放下的证明状态、模型假设、等待用户处理事项。

必须保持逐任务守恒：`原始剩余工作秒数 = 已安排工作秒数 + 未安排工作秒数`。舍入留白不属于工作量；历史投入不计入未来覆盖率。部分安排时不能用“已安排最后一块的结束时间”冒充整个任务完成时间。

推荐原因码：`CAPACITY_LOWER_BOUND`, `NO_CONTIGUOUS_WINDOW`, `DEPENDENCY_UNSATISFIED`, `DEPENDENCY_CANCELLED`, `PROTECTED_CONFLICT`, `OVERDUE_CUTOFF`, `WINDOW_LIMIT`, `ESTIMATE_REQUIRED`, `EXECUTION_UNCONFIRMED`, `CHECKPOINT_REQUIRED`, `GRID_RESOLUTION_CONFLICT`, `NOT_SELECTED_IN_RETURNED_PLAN`, `SEARCH_LIMIT_REACHED`。

可解释性的最低要求是指出相关任务、时段或数字，而不是只返回“优先级不足”。不能解释为已证明的原因，就使用诚实的搜索未决状态。

原始规格提及两组 JSON 示例，本次附件未包含。第 8 节表格保留为人工验算案例；开发时须创建对应 fixture，不声称优化器已经输出这些结果。

## 8. 具体全流程示例

以下任务、时间和日期完全是假设，不是用户实际日历。时区 Asia/Shanghai；2026-09-21 至 2026-09-23，每天 18:00–20:00 可用，每天上限 120 分钟。为便于手算，例子把默认缓冲显式改为 0，只检验这三个已提供窗口。

| ID | 任务 | 本轮剩余预留需求 | 条件 |
|---|---|---:|---|
| C1 | 概率论作业，交付型 | 90 分钟 | COMMITTED；周二 20:00 cutoff |
| K1 | 竞赛 baseline，交付型 | 60 分钟 | COMMITTED；周三 19:00 cutoff |
| K2 | 打包提交，交付型 | 30 分钟 | COMMITTED；依赖 K1；周三 20:00 cutoff |
| R1 | 方法 X 调查，限时探索 | 90 分钟 | PREFERRED；人工锁定周二 18:00–19:30 |
| L1 | 错题复习，交付型 | 150 分钟 | OPTIONAL；可拆 |
| M1 | 完整模拟赛，交付型 | 180 分钟 | PREFERRED；不可拆 |

总需求 600 分钟，总可用 360 分钟，全部安排至少缺 240 分钟。M1 单独也放不下，因为最长窗口只有 120 分钟。这是不同的两个证明，不能混成一个理由。

### 8.1 一份合法初始计划

| 日期 | 安排 |
|---|---|
| 周一 | 18:00–19:00 C1（人工锁）；19:00–19:30 C1；19:30–20:00 L1 |
| 周二 | 18:00–19:30 R1（人工锁）；19:30–20:00 L1 |
| 周三 | 18:00–19:00 K1；19:00–19:30 K2（条件预约）；19:30–20:00 L1 |

C1、K1、K2、R1 完整预留；L1 安排 90，剩 60；M1 剩 180。K2 并非此刻就可执行。此计划是可行例子，不声称唯一或最优。

### 8.2 周一 19:00，C1 实际投入 60 分钟后确认“还要 75 分钟”

新剩余是 75，不是 15，也不是原估计扣完后的 30。已发布的周一 19:00–19:30 C1 和 19:30–20:00 L1 在近期冻结区；周二科研块仍是人工锁。

在不解冻的情况下，C1 到周二截止前最多还能得到：已经冻结的 30 分钟＋周二 19:30–20:00 可改排的 30 分钟＝60 分钟，少于 75。即便别的所有安排都最有利，仍差 15 分钟。

默认不静默移动周一 L1，也不挤掉科研锁。报告两个不同数字：保持原计划时 C1 只覆盖剩余 75 中的 30，未安排 45；允许使用所有未保护空档也至少短缺 15。不能把“未安排 45”说成“至少需要解锁 45”。

### 8.3 用户明确释放周一 L1 的冻结保护

重排如下，既有 C1 30 分钟块和科研人工锁完全不变：

| 日期 | 新安排 |
|---|---|
| 周一 | 已执行 18:00–19:00 保留历史；19:00–19:30 C1 保留；19:30–20:00 增加 C1 |
| 周二 | 18:00–19:30 R1 保留；19:30–19:45 C1 收尾；19:45–20:00 留空 |
| 周三 | K1、K2、L1 的原安排不变 |

C1 剩余覆盖 `30+30+15=75`。L1 未来只有周三 30 分钟，未安排 120 分钟。周二最后 15 分钟不能拿来塞给仍需很多工作的 L1，因为它不是 L1 的完整短尾；应留空，而不是违规碎片化。

此时未来预约 285 分钟，未来窗口共 300 分钟，留白 15。当天已投入 60＋未来预约 60＝日上限 120，不重扣或重复计入需求。

### 8.4 后续实际完成

周二 C1 提交并确认验收后才变 DONE。R1 用完 90 分钟但没有检查点先变 REVIEW；记录“没有足够证据支持方法 X，停止本轮”后可 DONE，不能当作科研失败，也不能自动安排新 90 分钟。由“继续研究 X”决定才成立的实现任务保持 DRAFT。

周三 K1 的块结束但测试没通过时，K2 不得因日历时间到了而开始。K2 的条件预约标记受阻，剩余估计和实际提交截止重新审查。

## 9. 现在决定与以后替换

现在必须固定：两种任务的完成语义；due/cutoff 区别；计划与实际分离；剩余工作和舍入口径；部分安排与依赖语义；保护优先级；超载不是整体无解；日志幂等与版本原子应用；原因码的证据等级。

这些影响存量数据意义，错误后很难仅靠换算法修复。

以后可以替换：CP-SAT/其他后端/贪心；2 秒预算；14 天与 24 小时；粒度（但需要数据与模型迁移）；默认块长和缓冲；冷启动估计建议；软目标顺序；前端与存储；机器资源和外部日历接入。

V1 不引入：强化学习、深度知识追踪、自动知识图谱、科研收益函数、自动推断技能迁移、自动给疲劳/掌握/成功率小数评分。记忆复习以后可以作为有人工/外部来源的任务需求接入，而不改写本调度语义。

## 10. 验收和实现优先级

先做对象及事件语义、校验器、日志对账，再做简单合法排程，最后接优化器。优化器与兜底共享输入投影和输出校验器。仅有一份漂亮日历，不足以验收 V1。

发布 Gate：人工锁和近期冻结不被静默改动；任务不会因排足时间变 DONE；条件后继不会提前启动；超载时存在可解释的未安排项；超时不谎称无解；同一日志重试不重复扣量；过时求解结果不能覆盖新编辑。

## 11. V1.1 闭环规则与接口补齐

本节细化前文；代码不得自行选择不同口径。数值默认值可配置，事实与预约分离、幂等、守恒和保护授权不可省略。

### 11.1 编辑剩余量与释放多余预约

已接受的新估计即为新的真实业务状态，不为保住旧日历而拒绝保存。若编辑造成预约超出剩余需求，先计算调整提案；用户可在同一操作中“保存估计并应用调整”。未接受调整时仅保存估计，受影响旧预约标 invalid、coverage_state=HOLD，清楚显示待处理，不能继续宣称完整覆盖。

默认保留最早可用的块，缩短最后所需块，取消更晚多余块；缩短仍满足网格和短尾规则。MANUAL 变化必须在确认中列明并授权，FROZEN 变化可通过一份提案集中确认。无保护的未来块允许随估计编辑自动修整并返回 changes。用户若要保留释放后的时间，可选择转换为 ReservationHold（独立保留时段，不关联任务需求，消耗日历及日容量），不能假装任务还需要这些工作量。

例：锁定 14:00–16:00，剩余量改为 45 分钟。提案保留 14:00–14:45，释放 14:45–16:00；原块 ID 保留，块 revision 增加。转换保留时段则新建 hold ID。例：只剩 53 分钟，保留 60 分钟，工作量 53、舍入留白 7，不能将剩余改为 60。

### 11.2 工作块覆盖与逐任务状态

WorkBlock 独立字段：

- coverage_state=COUNTED|HOLD。COUNTED 才参与需求覆盖；HOLD 的 planned_work_seconds=0、rounding_padding_seconds=0，其完整预约记 hold_seconds。
- validity=VALID|INVALID|PENDING。INVALID 不得启动；不符合硬规则的占位仅是冲突展示，不能包装成合法工作块。
- start_eligibility=READY|CONDITIONAL|BLOCKED，与保护状态和生命周期分开。

COUNTED 块满足 reserved_seconds=planned_work_seconds+rounding_padding_seconds。所有输入信息齐全的计入覆盖块满足原剩余 W=覆盖工作秒数+未覆盖工作秒数。HOLD 消耗时间但不扣 W。输入不完整时，保留 last_known_remaining_seconds，current_remaining_seconds=null，覆盖为 0、未覆盖为 null，不做虚假守恒计算。

逐任务输出：coverage=FULL|PARTIAL|NONE|UNKNOWN；input_state=READY|ESTIMATE_REQUIRED|EXECUTION_UNCONFIRMED|CHECKPOINT_REQUIRED；horizon_state=IN_WINDOW|BEYOND_WINDOW|NO_WINDOW_INTERSECTION；dependency_state=READY|CONDITIONAL|BLOCKED。有期限且在窗口外用 BEYOND_WINDOW，无可放置时间交集用 NO_WINDOW_INTERSECTION；无期限任务正常为 IN_WINDOW。多个输入事项同时存在时存 action_required[]，input_state 采用上述清单中优先级最高者（按出现顺序，READY 仅在无事项时使用）。

forecast_end 仅在 current_remaining 已知、coverage=FULL、所有必要祖先也完整覆盖时返回；CONDITIONAL 可返回但必须标注 conditional=true。非完整覆盖或 HOLD 不返回完成预测。FULL 始终表示预约覆盖，不表示 DONE。

### 11.3 漏记、阻塞和局部修复

过期无日志的块移出未来计划并标 EXECUTION_UNCONFIRMED；不自动补记投入，不自动减少剩余。该任务及依赖其完成的后继停止新增自动块；已有未来块降为 HOLD，保留原保护信息。其他独立任务继续规划。用户批量核实时每项必须显式选择“未做”“已做并填写实际值”“仍不确定”，不可默认批量完成。

前置返工或取消使后继无法保持原条件时，后继预约降为 BLOCKED/HOLD。不受保护且失效的未来预约可自动取消；受保护占位须确认释放或移动。只有占位本身时间、容量等硬规则合法时才能放入可发布日历；其任务工作量仍为零。保护占位与新会议重叠时，proposal.application_status=BLOCKED，不发布冲突计划，但可返回 independent_preview 供查看，预览不能被当作已应用计划。

### 11.4 自动保护、人工锁和事务

常规模式先将 FROZEN 和 MANUAL 都固定。若存在更好取舍，可生成第二份 adjustment_proposal：允许修改 FROZEN，仍不修改 MANUAL；只有用户明确请求调整某些人工锁时，才生成包含这些 ID 的方案。第二份方案不自动应用。用户可选择严格模式，完全不生成自动保护调整方案。

提案至少包含 proposal_id、base_state_revision、policy_version、valid_until、changes、required_manual_release_ids、affected_task_ids、方案摘要和内容摘要 hash。用户确认绑定具体提案与修改清单，不能泛化成将来任意改锁的授权。确认时校验版本、时间有效性、授权 ID 集合及完整约束；失败返回 STALE_REVISION 或 STALE_TIME，重新生成提案。任务编辑、预算调整、时段取消/转换及对应审计在一个本地数据库事务中提交。提案确认接口用幂等键，重复请求不重复生成时段或日志。

### 11.5 活跃计时、跨日和未来覆盖

V1 同时至多一个 active timer。计时器记录 active segment 的起止与暂停，不只存 elapsed 总时长。active_seconds 不得大于墙钟区间；按本地自然日拆分 segment。关闭计时器时，在同一事务移除临时 L 并产生 H，禁止两者同时存在。手动日志没有 segment 时，若墙钟区间与其他日志重叠，先待核实，不猜测休息发生在哪一段。

RUNNING 任务在结束反馈前 input_state=EXECUTION_UNCONFIRMED，其运行块和未来占位不提供新的需求可行性证明；已确认过去投入不再次算作未来覆盖。运行块剩余时间按 T 计入容量，其未来占位按 P 计，不重复计。跨午夜的工作块和 hold 按区间在各日的交集分别扣容量。未确认预计结束时，不允许在未知运行尾部猜测空档；同日新增规划暂停，已知其他日期可单独返回。

### 11.6 期限、队列与可比较的方案

若 due、cutoff 都存在，要求 release≤due≤cutoff；仅有 cutoff 时要求 release≤cutoff。非法组合返回逐任务 INPUT_REQUIRED，不悄悄交换日期。target_at=due，否则 cutoff，否则 null；截止硬约束始终只用 cutoff。按时=forecast_end≤target_at，不能用 cutoff 掩盖 due 已过。

未来窗口内 COMMITTED 目标进入第一层按时完整预留序列。target_at<now 的任务不进入不可能改善的按时标志序列，而进入第三层补救队列；若 cutoff 已过则停止新增。第三层按 importance、target_at（null 最后）、manual_order、稳定 ID 排序，已过 due 且未过 cutoff 的任务保留原 target_at，因此同等级中先处理；用户可通过明确修改重要性作取舍。

比较器逐层比较：第一层 timely_full 布尔向量字典序最大；第二层旧块变更数最少，再位移分钟最少；第三层按候选队列的覆盖工作秒数向量字典序最大；第四层依次最少已完整安排任务的总迟期秒数、块数、同日相邻任务项目切换数，再按稳定排序比较开始时间。部分覆盖的迟期是 unknown，第四层不能据此宣称部分任务更准时；它只在前三层相同时作为摆放指标。重新平衡模式交换第二、第三层。

块 ID 由保留匹配确定：未变块先按 ID 保留，其余同任务按原开始时间一一匹配；新建 ID 不免除原块删除成本。删除一个旧块计一次变更，移动或改长度计一次，纯新增不计旧块变更。总位移仅对匹配块计算绝对开始/结束差。每个候选输出 score_components；不同快照、授权集合或模式的分数不可直接比较。求解器先后顺序不决定采用哪份方案。

### 11.7 时间推进、缓存与提案失效

存储 revision 不随每秒变化。缓存键包含数据 revision、policy_version、时区、窗口、重排模式、保护授权集合及网格化 now；但复用前仍必须检查 next_temporal_event 和实时容量。next_temporal_event 为未来块开始/结束、截止、释放时刻、进入冻结区的时刻、当地午夜与规划窗口变化中最早的一个。

有 active timer 时重新计算 L/T 和当日容量，不缓存原容量；没有事件变化且校验仍通过，可保留相同计划 ID。所有新自动块 start≥ceil_to_grid(now)。proposal.valid_until 默认不超过生成后五分钟及下一时间事件（取更早者）；now≥valid_until 必须重验/重算，不应用过期方案。用户在块开始后确认“已经在做”，通过执行入口记录事实，不把它伪装成新生成的过去预约。

### 11.8 最小接口与交付边界

V1 使用本地持久化与单用户；网络账户、多设备同步、外部日历写入暂不实现。保留 revision/幂等以处理单机多窗口与重试。时区默认 Asia/Shanghai，存 UTC instant 加 IANA 时区标识；V1 不开放运行中更换时区和任意复杂循环规则，循环课表先支持每周展开。扩大时区功能前必须通过相应集成测试。

领域接口：create/update_task、start/pause/finish_session、reconcile_execution、close/reopen_task、preview_plan、apply_proposal、list_day。每个写入请求包含 expected_revision 和 idempotency_key。一次编辑返回最新状态、action_required 与可选提案；planner 不直接写任务完成状态。

proposal 至少增加：application_status=READY|NEEDS_CONFIRMATION|BLOCKED；backend=GREEDY|OPTIMIZER|REVALIDATED_PREVIOUS；quality=HEURISTIC|FEASIBLE|OPTIMAL；proven_levels[]、score_components、valid_until、input_digest。FEASIBLE/OPTIMAL 只能描述实际后端证据，纯贪心 quality=HEURISTIC。调度异常不得丢弃已确认执行事实。

V1 先交付：任务增改、固定课表、日可用时间、周日历、手动锁定、执行计时和补记、剩余量反馈、合法贪心排程、变更确认、未安排原因、本地保存。CP-SAT 是后续增强，不阻塞这条闭环上线；研究模型、概率工期和学习掌握度暂不接入。
