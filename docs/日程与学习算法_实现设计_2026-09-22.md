# 日程与学习算法：可实现设计

2026-09-22。对应《主流平台设计调查_2026-09-22.md》。本文件是拟议实现方案，不是已完成的算法接入或运行报告。工程基础来自本轮现有源码核查；算法入口来自官方文档。平台功能不等于其内部算法公开，下面不声称复现任何闭源平台的内部实现。

## 结论与可靠性边界

全部值得吸收的设计都有明确的工程实现路线。日历、约束、事务和撤销可以通过程序约束与测试验证；估时、回忆、知识状态是预测，必须显示证据并用后续数据验证。组合后的系统能否改善学习，需要实际使用验证，不能由“用了成熟库”直接推出。

建议采用：确定性日历与任务模型 + 局部贪心整理 + OR-Tools CP-SAT 复杂排程 + 容量诊断 + 按类型估时 + FSRS 复习 + 练习证据。BKT 是后续可替换组件，语言模型负责输入草稿与解释。上述个人规模的非深度算法可先按 CPU 方案实现；本轮未安装新依赖或测量耗时，不承诺毫秒级响应。

## 现有代码可以复用什么

- `planner/domain.py`：任务类型、依赖图检查、实际执行日志、人工剩余量反馈、验收关闭。
- `planner/scheduler.py`：14 天贪心排程、预约保护、人工锁、覆盖状态、差异预览，以及发布前的约束检查。
- `planner/store.py`：SQLite 事务、幂等请求、状态版本、过时预览拒绝。
- 当前正式后端仍是同一每日整点窗口、15 分钟网格。20:30 截止、按天窗口、教学周课表和容器需要真正接入后端；交互预览中的限制不能当作正式后端已经具备的能力。
- 当前没有 CP-SAT、自动估时模型、FSRS 或 BKT。已有验证器可作为起点，但复用了排程的部分辅助函数；新版本应补独立实现的关键不变量检查，降低同一错误同时出现在生成与检查中的可能。

## 功能到实现的对应

| 功能 | 第一版实现方法 | 边界与验证 |
|---|---|---|
| 今日试排 | 对同一状态快照运行纯规划函数，生成只读投影 | 不写任务、日志或正式预约；接受前再校验版本和当前时间 |
| 学习时段容器 | 日历 Reservation + 内部 Allocation | 内部任务不能超装；容器和任务不重复扣减容量 |
| 长任务分多次 | 一个 Task 关联多次 Session、Allocation | 不复制任务伪造完成；净剩余量与时间预算分开 |
| 局部调整 | 固定顺序的最早可行插入，必要时局部 CP-SAT | 固定课、已执行记录、未释放的锁不动；失败保留原正式方案 |
| 全周调整与试排 | 滚动窗口 CP-SAT | 区分可行、最优、无解、未知；到时限后不能把未知叫作无解 |
| 截止前时间余量 | 窗口容量检查 + 最大流松弛诊断 | 同一空闲容量只分配一次；流可行仍需检查连续性和依赖 |
| 自动估时 | 同类型、同尺度的经验速度中位数 | 数据少时使用人工估计；区间先标历史范围，不冒充置信区间 |
| 考试阶段计划 | 内容清单 + 阶段日期 + 任务模板 + 容量分配 | 保留全课覆盖；新增补练不得静默增加日预算 |
| 间隔复习与轻负荷日 | FSRS + 有限复习窗口 + 日容量 | 未复习不更新记忆状态；延后产生的积压保留可见 |
| 学习状态与短测 | 题目证据表、知识点映射、延后复测；后续局部 BKT | 区分看过、会回忆、会独立解题；不给所有学科统一分数 |
| 本周/今天/截止分离 | 独立字段与状态转换 | 计划改期不改变外部截止；过去的计划不等于真正逾期 |
| 时段偏好与投入预算 | 允许时间集合、软偏好、日/周上下限 | 偏好不是疲劳诊断；最低投入不足时必须报告冲突 |
| 双周课表与例外 | 学期周次展开 + 普通 RRULE + 实例覆盖 | 不推测学期起点；节假日调课单独覆盖；改一次不改整组 |
| 材料导入和小测草稿 | 模型结构化提取 + Schema + 业务校验 + 来源定位 | 格式合法不等于内容正确；缺失字段保持未知 |
| 多设备、撤销和资料入口 | 本地缓存/操作队列、幂等命令、版本控制、补偿操作 | 不以整库旧快照覆盖新记录；网页链接不等于拥有观看进度接口 |

## 1. 先建立正确的数据对象

以下是逻辑对象，不要求第一批就拆成所有关系表。可先在现有版本化 JSON 状态中增加 schema_version，再逐步迁移；保留事务、校验和备份，避免为换算法重做整个应用。

| 对象 | 关键字段与含义 |
|---|---|
| Task | 稳定 id、项目、活动类型、剩余估计/预算、估计来源、前置条件、内容范围、完成标准 |
| PlanningIntent | task_id、bucket（本周/今天等）、planned_date；不代替 cutoff_at |
| CourseSeries | 学期起点、时区、星期、节次、week_set、起止日期；普通习惯另存 recurrence rule |
| OccurrenceOverride | series_id、original_occurrence_key、取消/替换信息 |
| Reservation | 占用日历的时间区间、固定/人工锁/可调整、所属项目、是否学习容器 |
| Allocation | task_id、reservation_id、分配工作量、内部顺序/起止；可以跨多个时段 |
| Session | task_id、执行时间段、active_seconds、已完成内容单位、记录来源；计划不自动转为实际 |
| Attempt | 题目及版本、知识点标签及版本、首次/复测、结果、是否提示、时间、来源 |
| ReviewItem | 要回忆的明确内容、FSRS 状态、实际 review log、模型版本 |
| ExamPlan | 截止、必须覆盖的内容、阶段范围、模拟卷要求、可调整练习预算 |
| Proposal | base_revision、now、模型与规则版本、变化列表、未安排内容、求解状态、到期时间 |

项目预算不额外创造任务，知识点标签不自动创建硬依赖。依赖也应区分“建议先学”“必须完成后才能执行”，避免将 AI 猜测的关系变成锁死日历的规则。

## 2. 日历展开与时间精度

先将固定课程、个人不可用时间和已锁定预约合并为不重叠区间，再从各日允许窗口中扣除。通勤按课程位置/用户规则增加缓冲，合并重叠缓冲后扣除，不能多次扣同一时段。

采用半开区间 [start, end)，使 15:00 结束与 15:00 开始不被误判重叠。建议自习安排先用 5 分钟粒度，适配 07:10、09:35、20:30 等时间；固定事件保留真实时刻，实际日志保留秒。粒度与最小学习块长是两件事，不能因为能定位到 5 分钟就生成大量 5 分钟解题任务。

例如实际剩余 53 分钟可以预约 55 分钟，但 2 分钟舍入留白独立记录。不得把剩余需求改成 55 分钟，也不得把留白写为学习记录。

教学周计算使用用户确认的学期周一。任意周集合（例如 11–14、16 周）直接按 week_set 展开，不能只靠单双周表示。普通重复事项可以复用 python-dateutil 的 rrule/rruleset；实例修改保留原 occurrence key，并参考 RFC 的 RECURRENCE-ID / EXDATE 语义。来源：[RFC 5545](https://datatracker.ietf.org/doc/html/rfc5545)、[dateutil](https://dateutil.readthedocs.io/en/stable/rrule.html)。

只有可见窗口附近的实例需要生成；跨学期容量预测可以按天聚合展开。所有实例生成应幂等，重复刷新不能增加重复课程。

## 3. 两级排程：快的日常整理 + 完整约束求解

### 3.1 快速局部整理

触发条件：移动、拉长、缩短一项任务后，用户选择“整理后续安排”。范围默认只到当天结束；固定块、正在执行块、已经完成块和未释放的人工锁不动。

```text
读取同一版本快照
固定不允许移动的时段
按原顺序遍历受影响任务
    在该任务合法窗口中，寻找满足连续长度的最早空档
    尊重前置、最晚截止、项目预算和原有拆分规则
    找到则暂放入候选方案
    找不到则记录未安排/改用局部求解器
独立检查候选 -> 展示差异 -> 应用前再检查 -> 一次事务提交
```

扫描排序后的区间即可实现，不要求学习模型。贪心没找到位置，只能报告“当前整理未排入”，不能证明不存在其他排法。最小范围策略可能牺牲全局可行性，因此需要单独的“调整本周”入口。

### 3.2 CP-SAT 模型

OR-Tools 官方调度模型提供区间变量、可选区间、不重叠约束和先后关系，可用于构造个人排程器。[官方调度示例](https://github.com/google/or-tools/blob/stable/ortools/sat/docs/scheduling.md)

以时间格为整数单位。对任务 i 的第 j 个可安排执行段定义存在变量 z_ij、开始 s_ij、长度 d_ij、结束 e_ij。存在时 e_ij = s_ij + d_ij；其工作量与舍入留白分开记账。

硬约束：

- 互斥：一个人不能同时执行两项学习任务。
- 窗口：区间必须落在可用时段，所有自习结束不晚于 20:30；固定晚课本身不受该自习限制。
- 保护：固定事件和未释放的人工锁的位置不变。
- 释放与截止：不得在可开始日期之前或硬截止之后执行；软目标日期可以迟到但须显示。
- 工作量：总预留不超过当前剩余需求的网格化值；整项交付可以采用“完整覆盖或明确未排入”，允许部分推进的任务另行标记。
- 拆分：不可拆任务只有一个完整执行段；可拆任务设置段数上限、最小段长与收尾例外。
- 依赖：硬前置尚未完成时，后续预约只能条件性安排；前置全部剩余量先被覆盖且预测结束早于后续开始。执行时再次检查实际完成状态。
- 投入：每日总量、项目上限、必要的最低投入分别定义。下限与其他硬约束冲突时输出冲突，不悄悄违反。

目标分层处理：先考虑已承诺且临近截止的需求覆盖，再减少软目标延期，接着减少改动的任务数、跨日移动和移动距离，最后改善时段偏好和碎片化。层级需要按用户承诺定义；不把所有指标混成没有解释的“学习收益分”。

严格的逐层最优需要每一层得到最优证明后再固定该层值。若只有 FEASIBLE，可保留当前方案并继续做受限改善，但只能报告“当前最好方案”，不能声称完成严格字典序最优。

滚动窗口默认沿用 14 天；远期只做截止前容量与阶段需求检查。可采用 1–2 秒作为初始交互求解预算，再按真实数据测试调整。这是待验证的产品目标，不是本轮性能实测。相同输入尽量使用稳定排序和固定种子；保留有效旧方案作为候选，避免无必要的布局漂移。

必须原样区分求解状态：OPTIMAL、FEASIBLE、INFEASIBLE、UNKNOWN、MODEL_INVALID。无解证明只适用于明确的时间窗口、离散粒度、分段上限及其他模型限制。[CP-SAT 状态定义](https://developers.google.com/optimization/cp/cp_solver)

### 3.3 容器如何避免重复占用

外层检查固定课、学习容器和独立预约互不重叠；容器内部再检查任务区间均在容器内且互不重叠。不要把容器与其子任务一起放入同一 NoOverlap 约束，否则它们必然互相冲突。

日历容量按外层占用计算一次，内部工作量按 Allocation 计算。第一版容器限定为一个项目，便于项目预算核算；多项目容器以后再加入明确的分摊规则。专注记录按 Session 计算，容器不是一条额外的实际学习日志。

## 4. 容量预警：先快速筛查，再诊断共享空档

最简单的必要条件是：同一截止窗口内必须完成的剩余总量，不得超过该窗口内适用的可用容量。单个任务的空闲时间不能相加，因为任务可能竞争同一批空档。总量够，也可能缺少连续时间或依赖顺序。

进一步可做最大流松弛：

```text
源点 -> 任务：容量为待分配剩余分钟
任务 -> 合法空闲区间：只允许在该任务释放/截止/允许时间内的连接
空闲区间 -> 所属日期：容量为区间长度
日期 -> 汇点：容量为该日剩余学习额度
```

先按释放、截止、允许时段等边界切开区间，保证每条边对应整个合法区间。固定课和不可用时间剔除；已承诺的具体任务分配同时扣除相应容量与任务需求。容器内尚未分配的分钟作为独立容量节点，只接收符合容器项目的任务，不能既从容量中扣除又要求内部任务占用新的外部空档。日期额度按实际投入及已承诺的具体分配扣减一次，空容器容量与普通空档共同受其限制。依赖和连续性可在这一层放松，软时段偏好不删边，以保持图模型是完整约束模型的松弛，而不是人为过严的筛选。

若最大流不足，完整问题在这些输入假设下也无法全部覆盖，最小割可定位争抢容量的任务和日期。若最大流足够，仅表示这个松弛模型能装下，仍需 CP-SAT 检查不可拆任务、依赖及预算等完整条件。[最大流官方实现](https://developers.google.com/optimization/flow/maxflow)

最大流差额是“在这个松弛模型中还未能分配的工作分钟”，不是保证在任意日期增加同样分钟就能解开全部约束。缺估时、缺学期起点或缺重要固定事项时应标记未知，不生成确定性缺口。

## 5. 估时：先用有尺度的经验统计

同一来源和同类活动有明确工作单位时，建议使用：

```text
单位速度样本 = 与已完成单位对应的实际专注分钟 / 已完成单位数
预计剩余分钟 = 剩余单位数 × 可比样本单位耗时的中位数
```

单位可以是阅读页数、视频原始分钟、同类小题数量。课程难度明显变化应重新分组；综合题、开放研究不强行用题数线性预测。视频倍率已隐含在实际耗时样本中时，不重复除以倍率。

展示样本数、来源、最近日期和经验范围。没有可比记录则保留人工 working/upper 估计，不给自称准确的预测。可以将建议与人工估计并列，由用户选择是否替换。

实际记录缺失保持缺失；计时结束不等于任务完成；单位未完成的投入不能拿来当完整单位工时训练。未完成、取消、中断、返工的记录照样保留，用于暴露样本偏差和提醒重新估计。

用按时间先后保留的后续任务比较模型与人工估计的绝对误差、低估比例和范围覆盖。只有样本量与稳定性支持时再引入更复杂的回归/分位数模型；不存在所有活动通用的“记满 N 次就一定够了”。

## 6. 考试计划：阶段模板、记忆需求和容量共同工作

考试计划包含覆盖清单和阶段截止，不能只存考试当天。对竞赛保留完整课程列表，已按用户说明完成/无需处理的内容不再生成任务；“全过一遍”作为范围约束。

```text
课程覆盖 -> 对应独立练习 -> 延后复测 -> 阶段混合练习 -> 整套模拟
```

这里按具体单元关联，不要求整个课程全部看完才能开始任何练习，也不要求任何一道复测没通过就锁住后续所有课程。硬先修和建议先学分别处理。

每周计算：覆盖剩余量、已知必需练习量、复习需求和模拟卷连续时段，减去已预留覆盖后进入排程。远期先用聚合估计，临近再展开具体题目，展开时替换原需求而不是重复加一份。

落后时依次尝试在已有项目时段中重新分配、使用用户预留缓冲、提出调整较低优先级项目的方案。补练会改变需求，因此要与日期容量重新核对；无法满足就展示差额和取舍。不能自动跳课，也不能突破 20:30 或静默扩大每天投入。

RemNote 的考试调度是此种分层的产品参考，但本方案不声称复现其闭源算法，也不把闪卡策略直接等同于竞赛题策略。[考试调度说明](https://help.remnote.com/en/articles/9102040-understanding-the-exam-scheduler)

## 7. 复习与轻负荷日：直接接成熟库，外层处理日程

py-fsrs 提供卡片状态、评分更新、下次复习时间、回忆概率和序列化。[官方库](https://github.com/open-spaced-repetition/py-fsrs)

```text
真实回忆结果 -> 更新 FSRS 状态和复习日志
FSRS 的建议日期 -> 形成带来源的复习需求
按知识主题组成学习时段 -> 检查当天容量 -> 用户安排
```

初期使用所选发布版本的默认参数，记录包版本与模型参数版本，不手抄一套会随版本变化的公式。延后并未发生回忆，因此不得更新为成功复习；实际复习发生时使用真实间隔。

轻负荷日是调整可用容量和有限的复习偏好，不是把所有到期卡片无限推后。建议先允许提前安排；需要晚于推荐日期时展示为延后并保留积压。若以后设定可接受的回忆概率下限，可以求一个候选复习窗口，但该下限是用户偏好、概率是模型估计，不是记忆保证。

同一天相关内容可以放入一个学习时段，底层仍保留逐项回忆证据；没有逐项记录时不伪造卡片日志。用户不背单词中的词汇暂由原 App 管理，本应用只接时间安排，除非以后有可靠的数据导入路径。

## 8. 掌握情况：证据先行，BKT 可替换

首版对每个明确知识点显示“是否学过、最近独立作答、提示情况、延后复测”。不会的判断必须来自实际表现；没有记录就是未检验。

课程观看、重复抄答案、提示后答对、首次独立答对、变式题答对是不同证据。只要加入新活动标签就自动提高掌握度，会造成系统性高估。

BKT 的基本形式在每个技能上维护隐含掌握概率 p，并用猜对 g、失误 s 和学习转移 T 更新。简化无遗忘版本：

```text
预测答对 = p × (1-s) + (1-p) × g
答对后 p_correct = p × (1-s) / 预测答对
答错后 p_wrong   = p × s / [p × s + (1-p) × (1-g)]
练习后的 p_next  = p_posterior + (1-p_posterior) × T
```

这是模型说明，不能随意指定一套参数就展示可信的个人概率。基础模型也没有自动处理任意长期遗忘、题目难度和多知识点综合题。官方 pyBKT 支持若干扩展，但仍需适合的数据。[pyBKT](https://github.com/CAHLR/pyBKT)

试点选边界明确的技能和带可靠答案的题目。提示题单独标记，不能直接按独立正确喂入基础模型；多知识点题不能对每个技能重复当作一条独立证据。把前期记录用于拟合、后期记录用于评估；比较近期表现基线，检查 Brier/Log Loss 和校准。重做同一道题与迁移到新题分开评估。

在证据不足时只显示原始表现，不显示精确掌握概率。即使模型预测改善，也只证明后续表现预测有所改善；是否减少错误、提高考试表现，仍需实际学习验证。

## 9. 小测、材料导入与下一项任务推荐

模型输出使用固定字段：课程/章节、原始来源位置、候选题目、答案依据、时长建议及其依据、需要用户确认的字段。使用 JSON Schema 限制结构，再由业务校验检查节次、日期、范围、重复、引用和前置关系。[JSON Schema](https://json-schema.org/understanding-json-schema/reference/object)

两层校验后仍不能保证生成题内容正确。教材配套题、可运行代码测试优先；生成小测先作为草稿，题目修订保留版本，避免旧错误答案继续影响状态。模型不能直接写掌握度、覆盖确认或正式日历。

“接下来做什么”第一版用可解释分层排序：先过滤当前不可执行的任务，再考虑已承诺且临近截止的内容、到期复习、前置补练、阶段覆盖要求，最后按当前空档长度和用户偏好挑少量候选。同级保留用户原排序，避免频繁跳动。每条推荐记录 reason_code，可解释为具体原因。

学习状态只调整练习建议，不改变用户要求的全课程范围；个人项目以产出检查点管理，不把运行时长转换为科研进展。

## 10. 预览、应用、撤销和多设备

所有排程后端统一返回 Proposal。预览不写正式计划；应用时同时检查状态版本、时间是否过期、硬约束和改动范围，然后一次事务提交。实际执行发生后，即使其他字段没变，旧计划也可能不再适用。

撤销保存本次修改涉及的旧字段与预期版本，以补偿命令执行。若相关对象后来被编辑或执行，不直接恢复整份旧数据库，改为提示冲突或提供新的合法调整方案。幂等键避免双击或网络重试生成重复任务和复习日志。

多设备初期采用一个权威服务端和客户端离线操作队列：新增记录带稳定 id，联网后去重；同一任务的并发修改做版本冲突处理。课程和截止冲突不能用无提示的最后写入覆盖。没有必要第一版就对所有业务对象引入通用 CRDT。

资料入口存 source_url、页码/视频分集/时间戳与关联任务。未接入可靠服务接口时，只做“一键打开与手动记录”，不声称自动同步 B 站观看或不背单词掌握状态。

## 11. 验证计划与工程顺序

以下是应执行的验收，不是本轮已通过的测试。

| 场景 | 预期结果 |
|---|---|
| 一项自习 20:00 开始、需 45 分钟 | 不排到 20:45；返回无法装入或调整建议 |
| 周一/周三固定课到 20:55 | 固定课保留；不追加晚课后的自习 |
| 90 分钟容器内放 60 + 45 分钟任务 | 明确超装 15 分钟；日历容量不能算成 195 分钟 |
| 53 分钟剩余任务按 5 分钟粒度排 | 55 分钟预约 = 53 工作 + 2 留白；实际工时仍未知 |
| 两个 60 分钟任务只共享一段 90 分钟空档 | 不能分别报告都可按时完成；容量诊断暴露竞争 |
| 总空闲 90 分钟、最长连续空闲 30 分钟，任务不可拆需 60 分钟 | 总量筛查可能通过，完整约束必须拒绝 |
| 贪心未找到但换顺序可以装下 | 标记启发式未排入；不能说已证明时间不足 |
| 求解器到时限返回 UNKNOWN | 保留有效旧方案或报告未找到；不报告无解 |
| 预览后新增固定课程，再应用旧预览 | 版本冲突拒绝；不覆盖新课程 |
| 同一完成反馈因网络重试提交两次 | 只写一条学习/练习记录 |
| 同一个重复事项仅改本周 | 其他周保持原始规则，重启后仍一致 |
| 学过课程但未独立做题 | 覆盖增加，能力保持未检验 |
| 复习任务被延后但未执行 | 保留到期与积压；不产生成功回忆日志 |
| 不提供实际工时直接勾选完成 | 完成状态可以改变，实际时长仍未知 |
| 追加竞赛补练后超预算 | 提出取舍，不删减用户要求的课程，不越过自习边界 |

小规模排程用穷举得到参照解，检查贪心与 CP-SAT 的合法性、覆盖差异；对日历展开、容器计量、重复请求和撤销做不变量及边界测试。求解器之外的验证器逐条检查发布结果。学习预测采用时间顺序验证，不随机混入未来数据。

建议实现顺序：

1. 后端接真实教学周课表、按天窗口、分钟级边界和计划日期字段；保留现有日志与事务。
2. 持久化拖放、容器、只读试排、局部整理和可靠撤销。
3. 容量诊断与可替换 CP-SAT 后端；小实例与现有贪心对照。
4. 练习证据、考试阶段任务模板、按类型估时。
5. 自建复习条目接 FSRS；材料提取与小测草稿按需调用语言模型。
6. 只有局部数据通过验证后，启用 BKT 等学习状态预测。

本轮新增本设计文件，未修改正式排程器、数据库或安装算法依赖。
